# FP32 throughput and exact Allegiance encoding — 2026-09-26

Keep the recovered campaign on IEEE forward arithmetic. The cheapest next candidate is an exact one-pass Allegiance encoder. BF16x9 does **not** provide a documented FP32 Tensor Core path on this RTX 5090. Explicit Triton TF32x3 and IEEE-forward/TF32-backward are separate experiments requiring numerical and end-to-end measurements before adoption.

This investigation used primary documentation and installed source/header reads only. No GPU operation, compilation, benchmark, process control, or modification of frozen training files was performed. The proposals below have no measured speedup yet.

**Hardware and installed API boundary.** NVIDIA lists RTX 5090 as compute capability 12.0, B200/GB200 as 10.0, and B300/GB300 as 10.3. “Blackwell” alone is insufficient to infer instruction or library support. [NVIDIA capability table](https://developer.nvidia.com/cuda/gpus).

Installed metadata under `/home/lva/.venvs/shards-preflight/lib/python3.12/site-packages/` reports Torch `2.14.0+cu130`, its CUDA toolkit requirement `13.0.3`, cuBLAS package `13.1.1.3`, and Triton `3.8.0`. These are package/header observations, not a runtime dispatch probe.

The local `nvidia/cu13/include/cublas_api.h:185,213` contains the BF16x9 math/compute enums, but enum presence says nothing about this GPU's implementation. No distinct TF32x3 compute enum was found there.

Ordinary `torch` matmul precision settings are not a TF32x3 selector. The inspected installed Inductor dot generator, `torch/_inductor/codegen/triton.py:1795`, explicitly emits either `input_precision="tf32"` or `"ieee"`. A default-precision environment variable cannot replace that explicit argument. This is evidence about that source path, not a claim that every possible Inductor path was audited. A new kernel should request TF32x3 explicitly and preserve an IEEE fallback.

**Bounded numerical experiments, in priority order.**

1. If learner backward is a significant measured fraction, try IEEE forward plus TF32 backward in an isolated runtime. Actor, archive actors, behavior verification, learner forward, and post-update verification must all remain IEEE. Compare gradients, norms, accepted KL, rejected-update counts, finite optimizer state, and frozen-policy strength against all-IEEE. Unchanged forward precision does not imply unchanged learning: approximate gradients alter updates. Global precision settings must be restored before every forward; configure warmup and graph capture consistently. Changing a Python precision flag after capture does not change the arithmetic of already captured kernels. This needs explicit graph/eager parity tests.
2. For TF32x3, first compile and inspect actual sm120-generated code, then compare against IEEE and an FP64 reference on retained real policy inputs, cancellation-heavy inputs, and checkpoint weights. Require the existing selected-log-probability guard across actor and learner batch sizes, not merely a mean matrix error. Test full PPO acceptance and post-update finite checks without relaxing any gate.
3. Only then time captured forward/backward and whole collection/update cohorts. [The actual policy](../model.py) uses `2048→H`, `H→H`, `H→64`, candidate `32→64`, and small batched score products, with H128/H256. Test actual actor/minibatch sizes and tail padding. Extra products, conversions, and narrow shapes can erase an advertised Tensor Core peak advantage. Keep FP32 log-softmax, ratios, reductions, and optimizer state.

These are proposed acceptance criteria, not assertions that TF32x3 is IEEE-equivalent or that mixed backward preserves playing strength.

**Exact Host opportunity.** [V3 Encoder lines 44–45](../experiments/HostV3/Encoder.cs) calls `AllegianceEffect.OwnedCount` seven times per encoded deciding player. [OwnedCount](../../../Assets/Scripts/Shards/Engine/ShardsDuelEffects.cs) scans Deck, Hand, Discard, PlayZone, and Champions each time. [CountsAs](../../../Assets/Scripts/Shards/Engine/ShardsEngine.cs) can repeatedly search the player's Destinies for Project Yggdrasil. This means seven owned-zone traversals and repeated definition lookup, although all seven results can be computed together.

A future isolated Host variant can clear seven stack-local integer counters, compute `hasYggdrasil` once, and traverse those five zones once. For each card, read its definition once and increment a seven-bit membership mask: always its printed faction; all five real factions if `CountsAsEveryFaction`; otherwise the additional Wraethe/Undergrowth identity under Yggdrasil. OR membership bits before incrementing so a printed faction is never counted twice. Include temporary fast-played cards, and exclude Destinies, Banished, and SetAside exactly as OwnedCount does. Divide each final integer by `20f` once; accumulating `0.05f` repeatedly would introduce avoidable rounding differences. Inspect only the deciding player's cards.

Before timing, compare membership against `CountsAs` for every catalog definition, every queried faction, and Yggdrasil on/off; cover Prism, temporary plays, and excluded zones. Require byte-identical full observations/candidates/masks and identical actions/rewards across seeded cohorts plus the existing privacy fixtures. A definition-to-membership-mask cache is optional after correctness, keyed by immutable catalog identity. The first one-pass version already removes the repeated scans; avoid complicating frozen rules or reusing permanent-only collection features, which omit temporary cards. Its benefit must be measured in encode time and whole training time before an identity-pinned handoff.
