# Representation and algorithm quality audit — 2026-09-26

The best immediate use of the current checkpoint is to keep training it while measuring strength against multiple frozen opponents. A representation extension can preserve learned behavior, but it requires an explicit, tested migration. Replacing PPO, introducing recurrent training, or restricting legal actions without a strength comparison is not justified by the current evidence or the remaining roughly ten-hour allocation.

This audit read the current `Encoder.cs`, `Adapter.cs`, policy, collector, and rules. It consulted original papers rather than secondary summaries. The only execution was a single-threaded CPU fixture in a separate temporary .NET project referencing the existing DLL. No GPU work, production source edits, live-host rebuilds, model updates, uploads, signals, or changes to the running campaign occurred. All recommended improvements below are unmeasured unless explicitly marked as verified.

## 1. A verified alias matters more than model width

The existing encoder preserves exact own permanent collection counts and several public zones. The candidate scorer embeds card identities, so this is already substantially better suited to variable legal menus than a fixed output head over every possible game action. However, more network width cannot recover distinctions which produce identical inputs. See [encoder](../Host/Encoder.cs), [adapter](../Host/Adapter.cs), [policy](../model.py), and [learning transform](../learning_model.py).

**Verified: temporary ownership changes Allegiance but can disappear from the complete observation and legal menu.** The own-collection channel deliberately excludes fast-played cards. The public-play channel includes them, but the public entity records have no `FastPlayed` or `BanishAtCleanup` field. Current candidates include these flags only when the particular instance is selectable. At a normal priority request, an already played ally usually has no candidate.

The isolated fixture produced these positions using actual catalog cards:

| Property | A | B |
| --- | --- | --- |
| Permanent collection, both cases | Three Crystals, Shard Abstractor, Fungal Hermit, Mainframe Abbot, Data Heretic | Same |
| Permanent card remaining in deck | Shard Abstractor | Fungal Hermit |
| Ordered public play zone | Three Crystals, temporary Shard Abstractor, permanent Fungal Hermit | Three Crystals, permanent Shard Abstractor, temporary Fungal Hermit |
| Hand | Mainframe Abbot | Mainframe Abbot |
| Gems / mastery | 0 / 8 | 0 / 8 |
| Recorded faction and ally play counters | Identical | Identical |
| Actual Order Allegiance count | **4** | **3** |
| All 2,048 observation + 2,048 candidate + 64 mask floats | **Exactly identical** | **Exactly identical** |
| Play the same legal Mainframe Abbot | Mastery becomes **9** | Mastery remains **8** |

Each case starts from a constructed, card-conserving position and executes five advertised, engine-accepted actions: three Crystal plays, then fast-buy/play in opposite orders. It is **not** a complete replay proving reachability from an ordinary initial seed; that stronger claim would require an acquisition/banishment history. The result does prove the real encoder aliases two internally consistent positions after legal action prefixes, and that the actual registered effect reacts differently. The discrepancy is not merely a hypothetical different deck order: temporary ownership is known from the player's own actions. [Raw result](representation-alias-fixture.json), [standalone fixture source](representation-alias-probe/Program.cs), [project](representation-alias-probe/Probe.csproj).

Rule source: [`AllegianceEffect.OwnedCount`](../../../Assets/Scripts/Shards/Engine/ShardsDuelEffects.cs) counts all play-zone cards, including fast-plays; [`mainframe_abbot_duel`](../../../Assets/Scripts/Shards/Content/ShardsDuelSet.cs) tests Order 4. That behavior is the user's intended rule. The repair belongs in observation coverage, not game rules.

A separate captured learned game reached a genuine nonterminal resource deadlock after both collections lost currency and usable damage generation. The [exact replay](learned-cap-replay.json) shows unchanged health from round 42 to 400. This is evidence to track deck depletion and censoring, not proof that the policy needs shaping rewards or a rule declaring such states draws. The current complete-episode censoring avoids fabricated outcomes, but learning remains conditional on completion.

These follow directly from [encoder](../Host/Encoder.cs), [adapter](../Host/Adapter.cs), [player turn state](../../../Assets/Scripts/Shards/Engine/ShardsState.cs), [decision contract](../../../Assets/Scripts/Core/DecisionRequest.cs), [Scry/reorder](../../../Assets/Scripts/Shards/Engine/ShardsDuelEffects.cs), and [split/defense flow](../../../Assets/Scripts/Shards/Engine/ShardsEngine.cs).

Additional architecture limitation: the policy/value state trunk sees only `obs`. Candidates are scored individually against a shared state query; they are not pooled back into the trunk. Thus candidate-only information, such as newly revealed Scry card identities, does not inform the value prediction. Pairwise logit differences are functions of the observation and those two candidates, not other menu contents. A small masked candidate-set pool or residual cross-candidate scorer is a sensible later ablation. It is not evidence that the current model cannot learn ordinary card choices. A shared set encoder has a principled permutation-invariant formulation in [Deep Sets](https://arxiv.org/abs/1703.06114); ordered zones must retain explicit position/role features.

## 3. A small extension can retain current weights

The catalog currently has **189 definitions**, while nine count channels reserve 192 each. Therefore 27 count-channel tail columns are always zero, as are scalars 110 and 111: **29 structurally unused input columns** under the pinned catalog. This was checked against `main/catalog.json` and encoder indexing. Public-entity padding is state-dependent and is not safely reusable.

A candidate schema-v3 extension could spend seven of these columns on the deciding player's exact `AllegianceEffect.OwnedCount` values. That repairs the demonstrated threshold distinction without exposing opponent secrets or changing the 2,048-dimensional wire shape. Other columns could cover exact played-type counters or typed decision quantities. This does not repair all per-card temporary status, all opponent history, or Scry memory.

To preserve behavior, use an explicit offline migration at an episode-free checkpoint:

1. Keep every old nonzero-capable input and its meaning unchanged. Pin the new field map and restrict the catalog to its reserved range, or relocate extensions before catalog growth; definitions 190–192 must never silently collide with new scalars.
2. In `core.trunk.0.weight`, set only the formerly always-zero input columns to zero. Copy all other weights. Zero the corresponding Adam moment columns while preserving their tensor layout, existing optimizer state elsewhere, update counts, RNG, next seed, and the authoritative time ledger.
3. Apply the same function-preserving conversion to learner, champion, initial policy, and every archived opponent. Newly filled features then initially contribute zero to all logits and values.
4. Verify the original and migrated functions on real stored observations, including large boards, Scry, splits, and defense. Compare old versus new authorized observations while checking logit/value parity, legal action sets, hidden-permutation privacy, and finite optimizer state.
5. Create a new explicit schema/source identity and lineage record. Existing strict resume should continue rejecting mismatched sources; do not weaken it to make migration convenient. Run a bounded charged continuation comparison on the same shared ledger before choosing whether to spend the remaining allocation on the migrated policy.

This is a feasible checkpoint-preserving design, **not an implemented or measured migration**. Preserving the old function at conversion does not guarantee subsequent learning improves. OpenAI Five's original report describes function-preserving architecture/observation changes and the need to convert historical opponents consistently; its much larger compute schedule does not supply a suitable warm-up duration for this machine. [OpenAI Five, Appendix B](https://arxiv.org/html/1912.06680v1#A2).

For a larger follow-up, append an auxiliary feature branch with a zero-initialized output projection into the existing state representation. It can consume a public-event ledger or revealed-card embeddings while initially producing exactly zero. This preserves the existing card policy as a starting point and lets an ablation decide whether the additional information justifies its throughput cost. Distilling into a different architecture is also possible, but consumes training budget and provides approximate rather than automatic exact preservation; [Policy Distillation](https://arxiv.org/abs/1511.06295) demonstrates this transfer approach in Atari, not Shards.

## 4. Action factoring: keep exact coverage, separate speed from policy changes

The adapter already factors damage amounts by integer intervals and general decisions by staged selection. Every legal answer remains representable; it does not have a fixed 64-action cap on the underlying game. However, exact coverage is not identical to unchanged exploration probabilities. Equal probability among unequal-width split intervals is not uniform over damage amounts. Unordered subsets can have several selection permutations; paging changes path length. PPO operates on this augmented sequence, so staged log-probabilities are valid for the sampled path, but wrapper entropy, step-weighted training, and policy priors introduce representational preferences. [Current adapter contract](../Host/CONTRACT.md).

| Proposed optimization | Rule/action coverage | Checkpoint compatibility and recommendation |
| --- | --- | --- |
| Skip policy sampling when exactly one legal action exists | Exact, if the engine action is still submitted and outcomes processed | Action log-probability is 0 and its policy gradient is 0. Value-loss/sample weighting and RNG advancement still need explicit treatment. Measure true forced-action frequency first; normal priority includes concede and is not forced. |
| Cache frozen per-card/static candidate features or state work across purely staged decisions | Exact if dynamic fields and staged trace remain correct | Best compatibility category. Current full observation changes during staging, so blindly caching the trunk is incorrect. Validate mathematical parity and measured wall-time. |
| Resolve the same autoregressive staged policy locally without an engine/pipe round trip between every subchoice | Exact answer coverage and potentially same policy distribution | Engine state does not advance until `SubmitSelection`, but staged observation/trace does. Reproduce those updates and retain every subchoice likelihood. Useful engineering prototype; not already supported. |
| Change split branching 8→64 | Exact integer coverage, changed staged policy | Existing weights can load, but behavior and path probabilities change. Requires a separate frozen-strength comparison and declared behavior version; not a transparent throughput change. |
| Automatically play all currency cards | Lossy | A played Crystal is no longer a hand/discard banish target; ordering also interacts with thresholds, copying and reveal effects. Keep optional macros only alongside primitives, or prove a narrow commutation condition. |
| Always reveal all shields | Lossy | Reveals information and removes deliberate defense choices; deferred champion protection makes face-damage-only heuristics incomplete. Do not call this rule-preserving. |
| Limit damage to zero, lethal, or a few buckets | Lossy | Removes legal allocations and potentially strategic taunt/shield decisions. A tactical proposal list can augment exact choices, not silently replace them. |
| Drop low-ranked buys or concede | Lossy | Changes the allowed game policy class. An exploration prior over still-legal choices is different from removing choices. |

Action branching can share features across action components, but independent component heads do not automatically handle the shared damage budget or taunt dependencies. Those require conditional masks/remaining-budget updates. [Action Branching Architectures](https://ojs.aaai.org/index.php/AAAI/article/view/11798). Keep engine-derived invalid-action masking; it has theoretical and empirical support for policy gradients and should not be replaced with penalties for rejected moves. [Invalid Action Masking](https://arxiv.org/abs/2006.14171).

## 5. Recurrent policy versus explicit history; PPO versus alternatives

**Prefer a small exact knowledge ledger before a general recurrent replacement.** Scry knowledge, public acquisitions/banishes, and played-this-turn counters have defined update rules. Encoding them can reduce partial observability without learning bookkeeping through long sequences. A per-seat ledger must never consume the other player's private observation. Keep player-specific knowledge through opponent turns; invalidate it only when a public event makes it stale.

A recurrent residual branch is a reasonable next-campaign comparison if the ledger still misses important inference. Recurrent training needs ordered per-seat sequences, terminal/reset handling, hidden-state versions, burn-in or controlled state initialization, and stored behavior probabilities. The current shuffled-row minibatch path cannot train an RNN correctly by merely adding a GRU to the network. Ni et al. found well-tuned recurrent model-free baselines competitive across many POMDPs, emphasizing architecture and training choices; that is a reason to test memory, not a guarantee it wins a ten-hour Shards budget. [Recurrent Model-Free RL](https://proceedings.mlr.press/v162/ni22a.html).

| Alternative | Evidence and relevance here | Decision for this campaign |
| --- | --- | --- |
| Current terminal-return PPO | PPO was designed for multiple minibatch epochs from a behavior batch. Current code already has action features, legal masking, owned trajectories and guarded updates. [PPO](https://arxiv.org/abs/1707.06347) | Preserve it unless a controlled comparison shows a clear strength-per-charged-second improvement. Changing epochs/learning rate is easier than replacing ownership semantics, but still needs a recorded config and valid continuation. |
| Deep Monte Carlo state-action value regression | DouZero showed strong imperfect-information card play using terminal returns, action encoding, parallel actors, and an LSTM over move history. Its published run used four GPUs over days. Its criticism of classifier-style policies does not directly apply to our candidate-feature actor. [DouZero](https://proceedings.mlr.press/v139/zha21a/zha21a.pdf) | Excellent next-campaign baseline. Current logits are not calibrated action values, so treating them as Q estimates would not preserve the trained policy. Similar complete-episode censoring concerns remain. |
| One-pass actor-critic/REINFORCE-style update | Can reuse current policy/value weights; fewer optimizer passes may reduce learner time, with higher variance or less reuse. This is an engineering hypothesis, not an established Shards result. | Only worth a short comparison if learner wall-time is material and sample efficiency remains adequate; raw updates/second is insufficient. |
| IMPALA/V-trace | Decouples acting and learning and corrects actor-policy lag. [IMPALA](https://arxiv.org/abs/1802.01561) | Potential scheduling follow-up. Requires new off-policy/trajectory correctness work and does not by itself solve opponent-policy drift, censoring, or missing observations. Not a drop-in way to reuse arbitrary old PPO rows. |
| NFSP / Deep CFR | NFSP targets average strategies via fictitious self-play; Deep CFR approximates regret updates from game-tree traversal. Their original poker results address exploitability, beyond simple self-play win rate. [NFSP](https://arxiv.org/abs/1603.01121), [Deep CFR](https://proceedings.mlr.press/v97/brown19b.html) | Long-term balance-study candidates. They require substantial additional algorithms/data paths and do not establish a favorable twelve-hour Shards result. Archive opponents are useful but are not equivalent to an equilibrium solver. |

Avoid attributing every failure to feedforward memory. The observed banishment deadlock can also arise from weak credit assignment, exploration, or policy quality even with fully observed own collections. Diagnose learning failures with concrete traces and matchups before replacing the algorithm.

## 6. Practical order of work while preserving the investment

1. **Now, without changing training:** collect rates for wrapper/engine actions, real completed games, censored games, per-kind actions, forced decisions, entity overflow, long staging, and learning/collection wall-time. Add only sidecar/new-file diagnostics; do not mutate the running checkpoint contract. The alias fixture establishes a capability gap but does not measure how often it harms play.
2. **At an available evaluation window:** test current frozen weights at their trained sampling distribution and a small temperature grid, plus initial/champion/older archive opponents and both seats. Temperature changes preserve weights but change behavior; report them explicitly. Argmax can be exploitable in imperfect-information games, so do not select it on one matchup alone. Use fresh development seeds, not the reserved final audit seeds.
3. **Most plausible short continuation experiment:** the small schema-v3 own-Allegiance/played-counter extension with exact function-preserving migration. Require parity, privacy, full-pool conversion, source lineage, unchanged shared ledger, and a predeclared short budget before measuring strength. Do not interrupt a productive run merely because the extension is plausible.
4. **Next campaign:** explicit public-event/reveal memory, a modest candidate-set/entity encoder, optional recurrent residual state, and a Deep Monte Carlo baseline. Evaluate at equal charged wall-time, including collection, optimizer work, checkpointing and failures—not equal learner steps alone.
5. **Balance analysis:** preserve separate results for policy version and observation/action abstraction. A weak score for a Scry card under a memoryless actor or an Allegiance card under the demonstrated alias is evidence about that actor, not proof the card is weak. Usage counts are observational; randomized card changes, matchup diversity and censor-rate reports are needed for balance conclusions.

The actionable conclusion is to preserve the current PPO investment, measure actual strength, and repair small, verified information losses through an explicit compatible continuation before considering a more expensive architecture or algorithm replacement. No paper reviewed demonstrates that a particular replacement would beat this trained policy within the remaining local budget.
