# Shards 1v1: systems design for a 12-hour RTX 5090 training budget

Research date: 2026-09-25. Scope: a fresh training system for the current C# rules engine, including all configured DLC and Duel of Doom. No previous AI implementation, training results, or throughput claims were used. This is a proposed architecture and measurement plan, not a completed trainer or a GPU benchmark.

## Recommendation

Start with the existing headless C# engine, a compact player-visible observation encoder, many independent games distributed across a small worker pool, and one Python process that owns the RTX 5090 for batched policy inference and learning. Benchmark a small CPU inference alternative alongside it. Make the choice on held-out playing strength per wall-clock hour, supported by pipeline measurements. A GPU-native game rewrite is a second project, justified only if measured simulation cost prevents the CPU version from meeting the sample budget.

The main optimization opportunity is probably the production and movement of useful decisions, not maximum neural-network size. “Probably” is an engineering hypothesis: the inspected engine is managed, branch-heavy, and pauses on individual decisions, while a modest tabular/card network can be computationally small. No all-DLC neural training throughput has been measured here.

A single GPU must share its time between acting and learning. High actor throughput with no time left for updates is ineffective; high learner utilization while actors starve is equally ineffective. Extra updates, a larger model, or deliberately expensive search can raise utilization without improving the final agent.

## Current engine seams worth exploiting

The existing verification project directly compiles the engine into a `net8.0` target; there is already a route to execute the rules without rendering or Unity scene work. [Engine.Verify.csproj](../EngineVerify/Engine.Verify.csproj).

`ShardsEngine` exposes `PendingInput` and `Submit`, and holds an active `IEnumerator<ShardsStep>`. This suggests a natural actor boundary: run one game until a real player choice is required, enqueue that choice, then work on another game. A snapshot is not automatically a resumable simulator clone: suspended iterator state and queued effects matter. [ShardsEngine.cs](../../Assets/Scripts/Shards/Engine/ShardsEngine.cs).

`ShardsSnapshotBuilder.Build` constructs object lists for visible zones, copies the viewer's owned cards, sorts that `FullDeck`, and computes display glow/killability/purchase hints. This is useful for the game client, but need not be the hot-path representation for training. Inspection establishes the work exists; profiling must establish its cost. Visibility also requires explicit checks: the original pre-fix audit changed only an opponent's private hand/deck allocation and made their Aegis Archivist appear in `ConditionGlowIds`, while every other serialized snapshot field remained equal. Conditional probes now run only for the viewer. The actor encoder must still implement and test a rules-authorized information contract instead of assuming every display field is safe. [ShardsSnapshot.cs](../../Assets/Scripts/Shards/Engine/ShardsSnapshot.cs), [original pre-fix observation audit result](observation-audit-2026-09-25.json), [corrected audit result](observation-audit-fixed-2026-09-25.json), [regression fixture](EngineProbe/ObservationAudit.cs).

One especially concrete performance candidate is `InitialCardCounts()`, called by every snapshot. It scans the catalog and calls `RelicIdsFor()` for each relic definition and player; each such call scans the catalog again and builds/sorts a new list. Setup counts can instead be precomputed or sent out of band once the catalog, DLC, and hero choices are fixed, with correct invalidation while drafting heroes. This is an inspected redundancy, not yet a measured attribution of snapshot time. [ShardsEngine.cs](../../Assets/Scripts/Shards/Engine/ShardsEngine.cs).

Proposed compact encoder:

- Encode the pending decision owner's perspective. The defending player can be the decision owner even during another player's turn.
- Build numeric fields directly into reusable arrays. Map definition strings to stable integer IDs once per frozen card catalog.
- Represent deck composition as counts or pooled embeddings, without copying or exposing deck order. Encode public zones, own hand, current resources, relevant flags, legal candidate descriptors, and request type.
- Preserve effective costs, effective defense, and other rule modifiers needed for decision quality. Omitting UI construction does not justify replacing dynamic rules with printed card values.
- Share static card metadata across games. Keep per-instance damage, exhaustion, ownership, and other changing information separate.
- Keep actor-visible information separate from any privileged diagnostic state. Differential visibility tests should show that hidden-hand/deck-order changes cannot alter the actor observation when public information is unchanged.
- Carry `game_id`, decision sequence, player, decision kind, policy version, and catalog/configuration fingerprint with each request. Reject stale responses rather than apply them to a new request.

All of these are new implementation proposals. Define permitted information from the agreed game rules and player-information contract, then verify each encoded field and legal-action behavior against that contract. Use existing snapshot fields only after individual visibility audits; snapshot equality is useful diagnostic evidence, not permission to expose a field. Performance results become meaningful only after this contract passes, including the demonstrated opponent-glow regression.

## CPU actors and GPU ownership

### First implementation

Use one C# process with a bounded worker pool and many resident game instances. Give each game exactly one owner at a time. Each worker advances its available games until they wait for inference. The Python process batches ready requests, evaluates the policy, samples masked legal actions, and returns compact results. Resident games are concurrency; they do not need one OS thread or one process each.

For the observed 5800X, a useful **measurement sweep**, not a prescribed optimum, is 4, 6, 8, and 12 simulation workers. Sweep the number of resident games independently, for example 64, 256, and 1,024. Retain CPU time for the Python scheduler, transfers, diagnostics, and the OS. SMT means 16 logical CPUs should not be assumed to provide twice the simulation throughput of 8 physical cores.

Start with a bounded batched binary transport. If transport appears materially in the profile, move payloads to shared-memory rings with explicit producer/consumer ownership and a small control channel. A shared buffer is not automatically CUDA-pinned memory; the straightforward implementation can copy a filled shared batch into a reusable pinned staging buffer. Do not claim zero-copy until every actual copy is measured.

Avoid a Python/C# boundary for each individual tensor field, per-choice JSON, one network inference per candidate, and one child process per game. Encode the state once and score all its legal candidates in a tensor operation. The current JSON adapter remains useful for debugging and human-readable replay, not necessarily high-frequency training transport. [ShardsEngineAdapter.cs](../../Assets/Scripts/Shards/Engine/ShardsEngineAdapter.cs).

Central inference has primary-source precedent in SEED RL, while Sample Factory investigates efficient asynchronous single-machine sampling. Their reported speedups are results for their environments and hardware, not Shards predictions. EnvPool independently identifies environment execution as a frequent RL bottleneck. These papers support the architecture questions, not a numeric promise. [SEED RL](https://arxiv.org/abs/1910.06591), [Sample Factory](https://arxiv.org/abs/2006.11751), [EnvPool](https://arxiv.org/abs/2206.10558).

### Batching and scheduling

Sweep inference batch buckets such as 64, 128, 256, 512, and 1,024. Pad candidates within a measured bound, carry a legal mask, and use an explicit overflow path for unusually large decisions. Never silently truncate legal actions to make a static tensor fit. If candidate counts vary widely, use a few size buckets and measure their padding overhead.

Use a maximum batching delay as well as a target batch size. Otherwise waiting for a full batch can deadlock or stall when too few games are ready. Continue another engine partition while one batch waits for the GPU. Record batch occupancy and p50/p95/p99 request latency; an average alone hides slow DLC effect chains.

Start with frozen behavior weights during each rollout collection phase and separately identifiable opponent snapshots. This makes correctness and policy-version accounting easier. Then test overlapping collection with learning. If overlapping, cap queues and log policy-version age, log-probability ratios, and discard rates. Asynchrony can improve wall time while damaging sample efficiency through stale policies, particularly with recurrence. [Sample Factory synchronous/asynchronous guidance](https://www.samplefactory.dev/07-advanced-topics/sync-async/).

One GPU-owning process can schedule inference and learner work without many CUDA contexts. Try short learner chunks between ready inference batches before adding concurrent streams. Separate actor and learner weight copies prevent inference from observing a partially updated model. CUDA streams can expose overlap but do not create extra compute; compare completed useful decisions plus updates per second and request tail latency.

Group historical opponents by policy version to form batches, but avoid spreading a small total ready queue across an excessive number of policy buckets. A large evaluation league need not imply that every league member has active games at every moment.

### CPU inference is a real alternative

A very small feed-forward policy may execute faster close to the C# simulator than through a GPU round trip, especially at low concurrency. Benchmark this path with the same observations and model outputs. The cost is competition for the eight physical CPU cores and weight-distribution complexity. If it wins, use the GPU mainly for batched updates. The selection criterion is end-to-end strength/hour, not a rule that every forward pass must run on the 5090. PyTorch explicitly notes that small networks can be CPU-bound, limiting the benefit of mixed precision. [PyTorch AMP recipe](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html).

### Managed allocation and logs

Profile legal-action enumeration, iterator/effect allocation, observation construction, and event logging independently. Reuse arrays and buffers where ownership is clear; profile before pooling complex mutable objects. Keep compact episode metrics for all games and detailed replay traces for a sampled subset and failures. Disabling event retention must preserve any rule dependencies and deterministic verification behavior.

Test GC settings rather than assuming server GC is always faster. Microsoft documents that server GC uses multiple heaps and dedicated threads and can become counterproductive across many simultaneously active processes. One controlled engine process avoids multiplying that configuration across hundreds of actors. [Microsoft GC guidance](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/workstation-server-gc).

## RTX 5090 software and numerical path

Use an isolated, pinned framework environment and prove `sm_120` eager and compiled execution before a timed run. PyTorch introduced Blackwell support with 2.7 and CUDA 12.8. That is historical compatibility evidence, not a recommendation to install an old release: the official 2.12 release already deprecates the CUDA 12.8 wheel and directs Blackwell users to CUDA 13.0+ wheels, with driver minimums of 580.65.06 on Linux or 580.88 on Windows. Select a tested stable version available at implementation time and record its full package lock. [PyTorch 2.7 announcement](https://pytorch.org/blog/pytorch-2-7/), [PyTorch 2.12 announcement](https://pytorch.org/blog/pytorch-2-12-release-blog/).

The observed driver number exceeds those documented minimums, but package installation and a successful forward/backward/optimizer/compile smoke test remain necessary. A CUDA version printed by a driver utility is not proof that the Python framework or its compiled kernels are installed.

Proposed precision ladder:

1. Establish a correct FP32 reference on fixed observation/mask batches.
2. Compare BF16 autocast for dense network layers, retaining sensitive policy/value computations and optimizer state in FP32. Compare logits, sampled distributions, losses, and a short learning curve.
3. Compare FP16 with appropriate loss scaling only if there is a measured benefit.
4. Consider FP8/FP4 only after profiling shows matrix compute dominates, the specific `sm_120` kernel path is supported, and numerical/playing-strength tests justify the work.

AMP is designed to choose lower precision for suitable operations and FP32 where range is useful; casting the entire model, logits, advantages, and losses to a low-precision dtype is not equivalent. [PyTorch AMP documentation](https://docs.pytorch.org/docs/2.12/amp.html). For this proposed RL implementation, perform masked log-softmax/log-probability ratios, advantage normalization, return accumulation, entropy, and diagnostic reductions in FP32 initially. Handle padded rows and all-invalid terminal rows explicitly; an all-`-inf` softmax can create NaNs.

A small set encoder or MLP, shared state trunk, and candidate-scoring head is a reasonable systems baseline. Trial widths such as 128/256/512 are tuning candidates, not an architecture conclusion. Reduce model size if inference dominates; consider a larger model only if it improves held-out play within the available budget. Observation ablations need separate strength and encoding-cost measurements: deleting information that costs only a few integer counts may save almost nothing.

## Compilation, copies, and static shapes

Warm all planned inference and learner shapes before the paid run where practical, and report cold-start cost separately. Measure eager versus compiled execution. `torch.compile(mode="reduce-overhead")` targets Python overhead using CUDA graphs; `max-autotune` may spend more time choosing matrix kernels. Dynamic shapes and graph breaks can trigger recompilation. A few padded shapes often make a cleaner benchmark than an unbounded set of candidate lengths. [torch.compile reference](https://docs.pytorch.org/docs/2.12/generated/torch.compile.html).

The compile-time break-even calculation is simple: if compilation costs `C` seconds and saves `d` seconds per invocation, it needs more than `C / d` invocations to pay back. Include all shapes, actor models, and learner variants in `C`. This is arithmetic, not an empirical speedup claim.

CUDA graphs replay against stable addresses and shapes. Capture warmup, input/output lifetime, and synchronization restrictions matter; CPU engine work is not captured. Avoid per-row `.item()` calls in the compiled path. Keep masking, sampling, and log-probability computation on the device, then return the action batch together. [PyTorch CUDA graph semantics](https://docs.pytorch.org/docs/2.12/notes/cuda.html).

Batch host/device transfers and retain learner minibatches/rollouts on device across repeated epochs when capacity permits. Use a small pool of preallocated pinned staging buffers, asynchronous copies, and explicit completion ownership. Pinning every newly constructed tensor on the hot path is additional work; pinning the whole replay store is unnecessary. NVIDIA recommends minimizing transfers and batching small copies, while cautioning that pinned memory is scarce and expensive to allocate. [CUDA best-practices guide](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/).

Do not reuse a pinned source until its upload completes, and do not read an asynchronously downloaded action batch before completion. PyTorch documents both hazards. These races can produce legal-looking but wrong training data and are correctness issues, not merely performance issues. [PyTorch pinned-memory guide](https://docs.pytorch.org/tutorials/intermediate/pinmem_nonblock.html).

For a rough memory budget, `P` FP32 parameters with FP32 gradients and two FP32 Adam moments require about `16P` bytes before activations, temporary workspaces, actor copies, or trajectory data. One million parameters therefore accounts for about 16 MB in those four arrays; BF16 autocast does not by itself halve all of them. This is explicit array-size arithmetic. For compact trajectories, 65,536 transitions at 1 KiB each require 64 MiB; one million transitions at 2 KiB each require about 1.91 GiB, before metadata and duplicate staging. Measure the actual schema, including candidate arrays and recurrent states, before selecting capacity.

## WSL-specific choices

On WSL, the Windows driver provides CUDA access; NVIDIA instructs users not to install a Linux display driver inside the distribution. The same guide documents limited pinned-memory availability, incomplete managed-memory features, and incomplete NVML queries. Use modest pinned buffers and measured CUDA timings instead of assuming every `nvidia-smi` field exists or is meaningful. [NVIDIA CUDA on WSL guide](https://docs.nvidia.com/cuda/wsl-user-guide/).

Keep compiler caches, Python environments, frequently updated logs, and temporary training buffers on the Linux filesystem. The repository is currently under `/mnt/f`; artifacts may be copied back there at bounded intervals. Microsoft recommends keeping Linux-tool workloads in the Linux filesystem for performance. This does not establish that the mounted path affects a fully in-memory engine loop; it matters for startup, builds, caching, and frequent writes. [Microsoft filesystem guidance](https://learn.microsoft.com/en-us/windows/wsl/filesystems).

Do not assume the card's advertised PCIe generation equals the negotiated link of this machine. Measure actual transfer latency/bandwidth, and record link information when exposed. Likewise, visible WSL RAM and free system memory are more useful than installed host RAM for sizing resident games and buffers.

## Why a GPU-native simulator is not the first step

JAX offers a credible route to a fully compiled simulator/learner if the simulator is expressed as pure array operations with bounded shapes. PureJaxRL demonstrates this approach in its own environments, and JAX's documentation makes static-shape restrictions explicit. Calling the current C# engine from JAX does not make the engine GPU-native. [PureJaxRL project](https://github.com/luchris429/purejaxrl), [JAX compilation model](https://docs.jax.dev/en/latest/notebooks/thinking_in_jax.html).

For this game, a port would have to replace object/iterator effect execution with a bounded state machine, represent card zones and pending effects as arrays, manage variable-length decisions, implement all expansion effects, and preserve visibility and RNG semantics. Branch divergence and padding may erase expected gains. Most seriously, fast but slightly different rules would invalidate the balancing study.

A GPU port becomes attractive when **all** of the following hold: the CPU engine plus compact encoder remains the measured bottleneck after practical fixes; more CPU capacity is unavailable; enough development time exists outside the 12-hour training allocation; and differential replay against the C# engine passes for full expansion coverage, including rare decisions and overflow paths. Porting only an approximate subset may answer a different game's meta.

JAX is also viable just for the learner, but then it still has the same CPU-engine transport boundary. Its current installation documentation recommends Linux CUDA 13 wheels and a sufficiently recent driver; choosing it does not remove the need to benchmark the boundary. [JAX installation](https://docs.jax.dev/en/latest/installation.html).

## Throughput equations and honest budget estimates

Count **real policy decisions**, automatic/forced resolutions, complete games, learner example-passes, and unique training positions separately. One card play with several optional follow-up choices is not one universal “frame.” Two seats in one game are not two independent matches. Repeated SGD epochs are not fresh experience.

Define measured quantities:

- `S(k)`: engine + legal-action + observation production capacity using `k` workers, in decisions/s, excluding neural inference waits.
- `B`: average observation/candidate bytes uploaded per decision, including padding.
- `W`: sustained relevant transfer capacity in bytes/s; latency can bind before bandwidth.
- `i`: measured GPU inference service seconds per decision at the actual batch mix.
- `l`: measured GPU learner service seconds per example-pass at the actual minibatch mix.
- `u`: learner example-passes per new decision, including replay or repeated epochs.
- `R`: sustained end-to-end fresh decisions/s during actual training.

For the first design, which serializes actor and learner GPU work while overlapping the CPU pipeline, ignoring overhead gives the optimistic stage-capacity bound:

```text
R <= min(S(k), W / B, 1 / (i + u*l))
fresh decisions <= R * usable_training_seconds
complete games approximately = fresh decisions / measured_mean_decisions_per_game
```

The GPU term adds acting and learning costs because this scheduling design gives them separate slices of the same accelerator. If actor and learner kernels run concurrently, replace that term with measured combined throughput: isolated kernel elapsed times do not yield a strict bound when complementary kernels overlap. Kernel interference, launch overhead, CPU sampling, opponent-only decisions, evaluation, pauses, and partial games must be measured in the end-to-end result. A fully serialized collection/update design instead pays the sum of CPU and GPU stage times; it cannot attain the optimistic pipeline bound merely by multiplying isolated rates.

Illustrative arithmetic only, **not projected Shards performance**:

| Sustained end-to-end decisions/s | Decisions in 12 uninterrupted training hours |
| ---: | ---: |
| 1,000 | 43.2 million |
| 5,000 | 216 million |
| 10,000 | 432 million |
| 50,000 | 2.16 billion |

These totals can still be unhelpful if the choices are repetitive, the agents fail to discover important lines, the rules are wrong, or training is unstable. Convert them into complete-match and rare-card-exposure counts using observed distributions. In particular, random-policy games do not establish late-training decision counts or speed: stronger policies can build longer effect chains and larger decks.

## Measurement gates and timed pilots

| Gate | Measurement | Decision it supports |
| --- | --- | --- |
| Rules and observation contract | Seeded complete games, hidden-information invariance, every decision kind, legal masks, rewards, terminal/truncation handling, reproducible failures | Whether throughput would produce trustworthy training data |
| Engine capacity | Game initialization separately; all-DLC decisions/s and complete games/s; decision-kind mix; allocation bytes/decision; GC pause time; 1/4/6/8/12 worker scaling | Whether simulator, allocations, or CPU scaling binds |
| Encoder/transport | Engine alone versus compact encoding versus client snapshot; binary round-trip at realistic batch sizes; bytes/decision; p95/p99 delay | Whether information representation or process boundary binds |
| GPU actor | Actual candidate distributions; eager/compiled FP32/BF16; batch-size sweep; H2D + forward + masking/sampling + D2H, not just matmul | GPU batch choice and CPU-inference crossover |
| Learner | Full forward/backward/optimizer timings, real losses and masks, example-passes/s, peak VRAM, compilation time | Affordable network size, minibatch size, and reuse ratio |
| Combined 10–20 minute smoke run | Fresh decisions/s, learner throughput, policy age, queue occupancy, errors, match length, memory slope, short held-out play | Whether isolated improvements survive integration |
| Pilot strength, inside the training budget | Same training wall time and opponent/seed suite for a few model/observation variants | Which system produces the strongest agent per hour |

The durations and sweep values above are proposed engineering limits. With the confirmed budget, correctness work, profiling, framework/kernel smoke tests, and pipeline preflight happen before the timed campaign. The full twelve training hours are shared by learning pilots, the main run, and any trained challengers; pilot learning is not free extra training. Frozen-model validation and the final balancing campaign run separately and may take longer. This investigation has not launched a GPU smoke test or a training run.

Persist the following at coarse intervals, with compact per-game summaries for balancing: elapsed wall time, unique decisions, complete matches, seat/opponent/configuration, wins/draws/truncations, legal-action counts, card acquisition/exposure, rollout policy version, actor/learner timing, allocation/GC, GPU memory, and checkpoint ID. Store reproducible seeds and action traces for failures and sampled audits. Logging every expanded object graph at every choice can become a new bottleneck.

Use GPU events or correct synchronization for GPU timings; host enqueue duration alone is misleading. Use a short PyTorch/Nsight trace to identify idle gaps, transfers, and tiny kernels; keep heavyweight profiling out of the main throughput measurement. NVIDIA's GPU utilization statistic reports the fraction of time that at least one kernel executes, not the fraction of peak arithmetic achieved. Nsight exposes SM, Tensor Core, and transfer metrics where supported. [nvidia-smi documentation](https://docs.nvidia.com/deploy/nvidia-smi/), [Nsight Systems guide](https://docs.nvidia.com/nsight-systems/UserGuide/).

Useful optimization decisions are falsifiable: if encoding is 30% of step time, removing half of its cost yields at most a roughly 1.18x step speedup before secondary effects; if inference is 5%, doubling its speed can improve that serial path only about 1.026x. Those are Amdahl-law arithmetic examples, not measured fractions. Optimize the largest measured constraint first.

## Operational allocation and stopping rules

Once a pipeline passes correctness and performance preflight, freeze the code/catalog/observation contract and package versions for the timed experiment. Save weights, optimizer state, learning-rate schedule, policy/league metadata, RNG states, and elapsed-budget counters. Count cumulative training wall time across learning pilots, the main run, and trained challengers, including their self-play collection and update scheduling; count neither just optimizer-kernel time nor just the final selected model's training. In-flight C# iterator state should not be assumed serializable; either explicitly support engine continuation or restart partial games on resume and record that fact. Never describe a resumed run as bitwise identical unless tested.

Keep validation checkpoints during training and select against a fixed opponent suite. Pause learning for separately accounted frozen-policy validation when necessary, then resume the cumulative training clock. Reserve the full twelve-hour allocation for training; no two-hour evaluation deduction is needed. After training, run the larger frozen cross-play and balance-data campaign on the same computer for as long as the required matchup/card-exposure confidence needs. Preserve the final league and catalog so that additional evaluation does not change the policies or the game being measured.

If CPU production binds, first reduce observation/allocation/logging costs and increase resident-game concurrency within measured RAM limits. If GPU launch/transfer latency binds, increase batch quality and apply compilation/graphs. If dense compute binds, test BF16, smaller models, and learner scheduling. If playing strength is flat, extra hardware utilization is not a solution: inspect reward, action coverage, opponent diversity, policy collapse, and observation limitations with the algorithm investigation.

The deliverable of the first implementation should be a reproducible curve of strength versus wall time plus a defensible data-generation rate. There is currently no evidence that this particular game, CPU, and GPU combination reaches any named sample target, and no basis to promise a solved or perfect AI in twelve hours.
